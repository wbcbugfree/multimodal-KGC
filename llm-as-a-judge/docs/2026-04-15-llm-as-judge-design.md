# LLM-as-a-Judge Design for Image-to-KG Evaluation

## Goal

Design a reusable LLM-as-a-judge workflow for evaluating image-to-RDF/Turtle outputs when ground-truth labels are unavailable, with `soil_health` as the target unlabelled use case.

The judge must first be validated on `vistext`, where generated TTL outputs can be compared against existing ground-truth-based `content_only` traditional metrics. If the LLM judge aligns with those metrics, the same no-gold judge can be used to evaluate `soil_health` prompting strategies.

## Scope And Isolation

In scope:

- A no-gold direct assessment judge for one generated TTL graph against one source image.
- A no-gold pairwise judge for comparing two strategy outputs for the same source image.
- A VisText validation pipeline that compares judge scores/preferences against existing `content_only` traditional metrics.
- A soil_health evaluation pipeline that reuses the validated judge without requiring ground truth.
- OpenAI GPT-family models as the intended default judge provider, with provider/model kept configurable.
- A strict isolation boundary: all LLM-as-a-judge scripts, prompts, intermediate files, and output reports live under `llm-as-a-judge`.

Out of scope:

- A gold-aware LLM judge mode.
- Diagram2Graph validation in the first implementation, because that dataset has not been reorganized/refactored.
- Replacing existing traditional VisText metrics.
- Human annotation UI or manual-review tooling.
- Adding or modifying files under dataset folders such as `vistext`, `diagram2graph_dataset`, or `soil_health`.

## Rationale

The judge must be validated under the same information conditions used for `soil_health`: source image plus generated TTL only. Therefore, the judge should not see VisText ground-truth TTL during validation. Ground truth is used only after judging, to compute traditional metric agreement.

Using OpenAI judge models for Gemini-generated triples reduces same-model self-preference risk. This follows the concern identified in KGEval-style studies: evaluator identity can bias scores, especially when the judge evaluates outputs generated by the same model family.

`content_only` is the primary validation target because it evaluates literal-valued content plus chart type while avoiding fixed ontology triples that can inflate structural scores. This is a better proxy for image-to-KG extraction quality than full-graph scores.

## Data Flow

### Direct Assessment

For each available generated TTL file in a strategy output folder:

1. Resolve the source image by `img_id`.
2. Read the generated TTL.
3. Send the source image, generated TTL, ontology/task instructions, and rubric to the judge model.
4. Require strict JSON output.
5. Store one judge record per `(dataset, strategy, img_id, judge_model)`.

The direct judge output should include:

- `visual_faithfulness`: integer score from 1 to 5 indicating whether RDF claims are supported by visible image content.
- `coverage`: integer score from 1 to 5 indicating whether important visible information is represented.
- `schema_correctness`: integer score from 1 to 5 indicating whether RDF/Turtle follows the expected task ontology and structure.
- `value_accuracy`: integer score from 1 to 5 indicating whether labels, entities, and numbers are correct or acceptably close given image-only extraction.
- `specificity`: integer score from 1 to 5 indicating whether the graph is specific to this image and not generic.
- `overall_score`: integer score from 1 to 5 reflecting the judge's holistic quality assessment.
- `criteria_mean`: numeric unweighted mean of the five criterion scores, computed by the handler rather than trusted from the model.
- `major_errors`: concise list of missing, unsupported, or incorrect content.
- `reasoning_summary`: short explanation suitable for audit.

### Pairwise Comparison

For each image with outputs from at least two strategies:

1. Resolve the source image.
2. Read TTL A and TTL B.
3. Ask the judge to compare both outputs against the image, without seeing ground truth.
4. Require strict JSON output.
5. Store one pairwise record per `(dataset, img_id, strategy_a, strategy_b, judge_model)`.

The pairwise output should include:

- `winner`: `A`, `B`, or `tie`.
- `criterion_preferences`: per-criterion winner or tie.
- `confidence`: low, medium, or high.
- `reasoning_summary`: short explanation focused on visible evidence and RDF quality.

## VisText Validation

The validation pipeline uses the existing VisText strategy folders:

- `vistext/extract_rdf_ttl/vistext_zeroshot_outputs`
- `vistext/extract_rdf_ttl/vistext_oneshot_static_outputs`
- `vistext/extract_rdf_ttl/vistext_oneshot_dynamic_outputs`
- `vistext/extract_rdf_ttl/vistext_fewshot_outputs`

The pipeline evaluates whatever TTL files are present. It should work for the current 5-file pilot outputs and automatically scale when the full dataset is generated into the same folders.

The VisText folders are read-only inputs for this workflow. The judge pipeline may read images, generated TTL outputs, ground-truth-derived traditional metric reports, and labels as needed, but it must not write new files under `vistext`.

Validation joins direct judge records with existing traditional metric records from:

- `vistext/evaluation/vistext_llm_evaluation_results.json`

Only `content_only` metric records are used for validation.

Primary agreement checks:

- Spearman correlation between judge `overall_score` and `content_only.triple_match_micro.f1`.
- Spearman correlation between judge `overall_score` and inverse `content_only.normalized_ged`.
- Spearman correlation between judge `value_accuracy` or `coverage` and relevant content-only exact-match scores.
- Strategy-level ranking agreement between average judge scores and average traditional metrics.

Pairwise agreement checks:

- For each image and strategy pair, derive a metric winner from `content_only` traditional metrics.
- Compare the metric winner with the LLM pairwise judge winner.
- Report agreement rate, tie rate, and disagreement examples.

Disagreement cases should be preserved because they are scientifically useful. They may show either judge weakness or cases where traditional metrics miss semantic/image-grounded quality.

## Soil Health Evaluation

After VisText validation, the same no-gold judge runs on soil_health strategy folders:

- `soil_health/extract_rdf_ttl/zeroshot`
- `soil_health/extract_rdf_ttl/oneshot_static`
- `soil_health/extract_rdf_ttl/oneshot_dynamic`
- `soil_health/extract_rdf_ttl/fewshot`

Direct assessment produces per-output quality scores. Pairwise comparison produces strategy preferences per image. Since soil_health has no ground truth, only judge results and aggregate strategy summaries are reported.

The soil_health folders are read-only inputs for this workflow. The judge pipeline may read source images and generated TTL outputs, but it must not write new files under `soil_health`.

## Architecture

All implementation files should live under `llm-as-a-judge`. The existing dataset folders remain read-only dependencies.

Shared judge utilities:

- `llm-as-a-judge/llm_as_judge/prompts/direct_image_to_kg_judge.md`
- `llm-as-a-judge/llm_as_judge/prompts/pairwise_image_to_kg_judge.md`
- `llm-as-a-judge/llm_as_judge/judge_core.py`

Dataset-specific CLIs and path adapters:

- `llm-as-a-judge/evaluate_vistext_judge.py`
- `llm-as-a-judge/evaluate_soil_health_judge.py`

Expected output artifacts:

- `llm-as-a-judge/results/vistext_llm_judge_results.json`
- `llm-as-a-judge/results/vistext_llm_judge_validation.json`
- `llm-as-a-judge/results/soil_health_llm_judge_results.json`

The judge folder can also contain local caches and run manifests, for example:

- `llm-as-a-judge/results/cache/`
- `llm-as-a-judge/results/manifests/`

## Configuration

The judge CLI should support:

- `--judge-provider`, default `openai`.
- `--judge-model`, required unless `OPENAI_JUDGE_MODEL` or `openai_judge_model` is configured.
- `--strategies`, optional subset of strategies.
- `--sample-mode`, with `all`, `random`, and `ids`.
- `--sample-count` and `--seed`.
- `--modes`, with `direct`, `pairwise`, or both.
- `--skip-existing`.
- `--output`.

API keys should use existing `common.get_api_key`, with `OPENAI_API_KEY` or `openai_api_key` as the expected OpenAI key names.

## Error Handling

The judge runner should:

- Validate that generated TTL files are parseable before judging.
- Record parse failures rather than sending invalid TTL to the judge.
- Require strict JSON judge output and retry on malformed JSON.
- Record API errors, parse errors, prompt/model metadata, and retry attempts in the output file.
- Avoid overwriting successful previous judge records unless explicitly requested.

## Reporting

VisText validation report should include:

- Run metadata: judge provider, model, timestamp, strategy folders, graph mode reference.
- Direct judge summaries per strategy.
- Correlations against `content_only` traditional metrics.
- Pairwise agreement against metric-derived winners.
- Per-image disagreement records for later inspection.

Soil health report should include:

- Direct judge summaries per strategy.
- Pairwise strategy preference matrix.
- Per-image direct and pairwise records.
- Parse/API failure summaries.

## Success Criteria

The design is successful if:

- The same direct judge can run on both VisText and soil_health without using gold labels.
- VisText validation quantifies alignment between judge scores and `content_only` traditional metrics.
- Pairwise judge preferences can be compared against metric-derived VisText preferences.
- The soil_health report can rank prompting strategies and preserve judge explanations for audit.
- The implementation remains folder-driven, so it works for the current pilot outputs and future full-dataset outputs.
