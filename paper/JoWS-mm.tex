\begin{abstract}
% Scientific knowledge is frequently communicated through visual artifacts such as charts, tables, and flow diagrams. Although these artifacts often contain compact empirical or procedural knowledge, they are difficult to reuse in Semantic Web applications because their content is encoded visually rather than as machine-interpretable triples. This paper studies image-to-knowledge-graph construction as a direct image-to-RDF task. We design a prompting-based framework in which a large vision-language model receives an infographic image and returns an RDF/Turtle graph. We construct two labelled image-to-RDF resources for evaluation: a VisText-derived chart-to-RDF dataset covering train, evaluation, and test splits, and a Diagram2Graph-derived diagram-to-RDF dataset obtained by expressing the original graph annotations in a lightweight RDF schema. We evaluate zero-shot, one-shot, dynamic one-shot, and few-shot prompting strategies where applicable, using both exact graph-matching metrics and softer graph-similarity metrics. For unlabelled scientific images, we introduce an LLM-as-a-judge framework adapted from KGEval and validate it on the two labelled datasets before applying it to an unlabelled domain application. The study provides datasets, methods, and an evaluation framework for assessing direct RDF extraction from scientific images under both labelled and unlabelled conditions.

\section{Introduction}\label{sec:intro}

Scientific communication relies extensively on visual artifacts. Charts summarize quantitative trends, tables arrange measurements and qualitative categories, and diagrams describe procedural or causal relations. However, such artifacts are often weakly represented, or entirely omitted, when scientific documents are converted into machine-readable corpora. In a typical retrieval-augmented generation workflow, for example, documents are first parsed into textual chunks or other retrievable representations before downstream question answering or analysis is performed \citep{rag_survey}. Visual elements whose meaning is encoded through marks, axes, layout, and topology can therefore be filtered out during preprocessing, even when they contain essential empirical or procedural knowledge. This omission limits both corpus construction and downstream structured knowledge acquisition from scientific literature.

Knowledge graphs provide a principled way to address this gap by representing entities, relations, and attributes in graph-structured form \citep{hogan2021knowledgegraphs}. RDF represents such information as subject-predicate-object triples, while ontologies define the classes and relations that make these triples interpretable and reusable. In the Semantic Web setting, RDF graphs can be validated syntactically, queried, linked to external resources, and integrated across domains \citep{rdf11concepts,turtle}. Directly converting scientific visual artifacts into RDF therefore offers a route from overlooked image-based evidence to explicit, queryable, and interoperable knowledge.

Existing research addresses important parts of this problem, but not the complete image-to-RDF task. Chart-understanding benchmarks and models focus on chart question answering, chart-to-text generation, or data recovery \citep{chartocr,chartqa,vistext,unichart,chartllama}. Diagram-understanding work can extract graph-like representations, but the target format is usually JSON, Mermaid, or another task-specific serialization rather than RDF \citep{diagram2graph,flowlearn}. Table-understanding systems increasingly process table images directly, but they commonly return reconstructed tables or task-specific answers rather than knowledge graphs \citep{mmtable,tabpedia}. Conversely, Semantic Web table interpretation typically assumes that tabular data are already available in textual or structured form \citep{semtab2022,semtab2024}. These lines of work motivate direct image-to-RDF construction, but they do not provide an end-to-end framework for producing RDF knowledge graphs directly from heterogeneous scientific images.

This paper studies such an end-to-end formulation. We use Gemini 3 Flash \citep{googledeepmind2025gemini3flashcard} as a large vision-language extraction engine and constrain its output to RDF/Turtle under predefined schemas. The framework is prompt-based and does not require task-specific fine-tuning. This design avoids decomposing visual interpretation, graph construction, and RDF serialization into independently optimized stages, a choice that is consistent with evidence from information extraction that pipeline architectures can propagate upstream errors, whereas joint models can reduce this dependency and improve extraction performance \citep{li2017neuraljoint}. We compare zero-shot, one-shot, few-shot, and dynamic one-shot prompting where applicable.

The main contributions are as follows:
\begin{itemize}
    \item We propose an end-to-end prompting framework for constructing RDF knowledge graphs directly from scientific visual artifacts, including charts, tables, and diagrams. The framework supplies the ontology in the prompt, optionally provides image-to-RDF demonstrations, and requires parseable Turtle output.
    \item We construct two labelled image-to-RDF datasets for systematic evaluation. From VisText \citep{vistext}, we derive RDF graphs that encode chart type, title, axis titles, and data points across the full train, evaluation, and test splits, while using only the test split for LLM evaluation. From Diagram2Graph \citep{diagram2graph}, we transform diagram annotations into a compact RDF schema that preserves node-edge semantics.
    \item We develop an LLM-as-a-judge framework for evaluating image-to-RDF outputs when reference graphs are unavailable. The framework adapts the rubric-based assessment idea of KGEval \citep{kgeval}, supports direct and pairwise judging modes, and is validated on the two labelled datasets before being applied to an unlabelled soil-health image collection.
\end{itemize}

Taken together, these contributions establish a reproducible experimental setting for image-to-RDF extraction. The paper does not claim that prompting alone resolves all visual graph construction problems. Instead, it characterizes the capabilities and limitations of prompt-based RDF generation, provides labelled resources for systematic evaluation, and offers a validation pathway for judge-based assessment when ground truth is unavailable.

\section{Related Work}\label{sec:related}

\subsection{Multimodal Understanding of Charts, Tables, and Diagrams}

Chart understanding has been studied through data extraction, question answering, captioning, and chart-specific foundation models. ChartOCR recovers data from chart images by combining visual detection and post-processing \citep{chartocr}. ChartQA introduced a benchmark for chart question answering that requires both visual and logical reasoning \citep{chartqa}. VisText formulates semantically rich chart captioning over chart images and chart-derived information \citep{vistext}. UniChart and ChartLlama further demonstrate that chart-specific pretraining and instruction tuning can improve multimodal chart reasoning \citep{unichart,chartllama}. These studies show substantial progress in chart perception, but their primary targets are captions, answers, or recovered data tables rather than RDF graphs.

Visual table understanding similarly focuses on reconstructing table structure or answering questions over table images. Recent work such as Multimodal Table Understanding and TabPedia studies large vision-language models for table perception and comprehension \citep{mmtable,tabpedia}. These systems are relevant because table images are one visual source considered in this paper, but their target outputs differ from the RDF/Turtle graphs required for Semantic Web integration.

Diagram and flowchart understanding is closer to graph construction because the visual artifact itself often represents nodes, edges, and labelled transitions. Diagram2Graph extracts structured graph data from process and flow diagrams into JSON \citep{diagram2graph}. FlowLearn evaluates large vision-language models on flowchart understanding and topology reconstruction \citep{flowlearn}. Work on circuit diagrams also emphasizes that topological extraction is difficult and can benefit from modular visual parsing pipelines \citep{circuitdiagram24}. Our work differs by normalizing diagram outputs into RDF/Turtle and evaluating the same image-to-RDF interface across multiple visual genres.

\subsection{LLM-Empowered Knowledge Engineering}

Knowledge engineering includes ontology modelling, entity and relation extraction, schema mapping, graph construction, refinement, and evaluation. Recent work argues that LLMs and knowledge graphs are complementary: knowledge graphs provide explicit symbolic structure, while LLMs provide flexible language understanding, generation, and reasoning capabilities \citep{pan2024llmkgroadmap}. LLMs have therefore been studied as extractors or assistants for constructing graph fragments under predefined schemas and for supporting RDF construction or ontology mapping \citep{ghanemcruz2025kgc,mavridis2025rdfkg}. However, most such work still assumes textual or already structured inputs, including semantic table interpretation benchmarks such as SemTab \citep{semtab2022,semtab2024}. Multimodal knowledge graph research also links images and text to graph entities \citep{richpedia,multimodalkgsurvey}, but this differs from constructing RDF triples from the semantic content of an image itself.

A small number of recent studies move closer to image-based knowledge graph construction. For example, ImgGraph-LLM constructs graph triples from individual images through self-supervised data generation and LLM fine-tuning \citep{chen2025pixels}. This shows that image-to-graph construction is becoming a research topic in its own right. However, existing work remains limited with respect to direct RDF/Turtle generation from scientific visualizations under explicit ontological schemas. In this paper, the image itself is the source document from which RDF triples must be extracted. The resulting graph describes the semantic content of the image rather than merely attaching image resources to existing graph entities.

\subsection{LLM-as-a-Judge and Knowledge Graph Evaluation}

LLM-as-a-judge methods use language models to assess generated outputs when human evaluation is costly or when automatic metrics are incomplete. Surveys of this area describe LLM-based judging as a rapidly expanding evaluation paradigm, but also emphasize that reliability depends on task design, calibration, bias control, and validation against external evidence or human judgments \citep{gu2024llmjudge}. MT-Bench and Chatbot Arena showed that model-based judgments can be useful for open-ended language-model evaluation, while also raising concerns about bias and calibration \citep{mtbench}. For knowledge graphs, KGEval proposes using LLMs to evaluate knowledge graph construction quality through criteria such as relevance, correctness, informativeness, and coherence \citep{kgeval}.

This paper follows the same general principle but adapts the rubric to image-to-RDF extraction. The judge receives the source image and the candidate RDF/Turtle graph, and it is asked to assess whether the graph is faithful, informative, coherent, and specific with respect to the visible image content. We also avoid using the same model family for generation and judging. This design choice is motivated by evidence that LLM judges can exhibit self-bias and family-bias, assigning overly favourable ratings to outputs produced by themselves or by related models \citep{spiliopoulou2025playfavorites}. Using a different model family for the judge does not remove all evaluation bias, but it reduces one avoidable source of confounding. Because judge-based evaluation can itself be unreliable, we first validate it on labelled datasets before using it for unlabelled scientific images.

\section{Materials and Methods}\label{sec:method}

\subsection{Task Definition and Target Representation}

Let $x$ denote an input image and let $\mathcal{T}(x)=\{(s,p,o)\}$ denote the RDF triple set generated for that image. The task is to produce a Turtle serialization of $\mathcal{T}(x)$ that faithfully represents the information visible or directly implied by the image. The output is not a caption or a natural-language explanation. It is a knowledge graph fragment whose classes, entities, and predicates are defined by a dataset-specific schema.

This study focuses on two labelled image families: statistical charts and flow/process diagrams. For charts, the target graph captures the chart type, title, axes, and data points. For diagrams, the target graph captures nodes, visible node labels, node types, directed edges, edge labels, and edge semantics. In all cases, syntactic RDF/Turtle validity is treated as a prerequisite for evaluation because malformed graphs cannot be used directly in RDF tooling.

\subsubsection{VisText-derived Chart-to-RDF Dataset}
VisText was originally introduced for semantically rich chart captioning \citep{vistext}. We derive a chart-to-RDF dataset by defining a compact reference graph for each usable chart image. The target graph contains one chart resource typed as a bar, line, or area chart; the visible chart title; x-axis and y-axis resources with their visible titles when present; and one datapoint resource for each observation represented in the plot. Each datapoint records its x-value, y-value, and membership in the chart.

The VisText task requires recovery of both explicit textual elements and visually encoded quantitative content. This distinction is especially important for line and area charts. In many such images, individual datapoints are not directly labelled; the model must infer the intended number of observations from the chart title, axis titles, tick marks, temporal range, and plotted marks, and must then estimate the corresponding values from the visual geometry of the plot area. In the case shown in Figure~\ref{fig:vistext_example}, the model must infer from the chart title that the area chart should contain one datapoint for each year in the reported period.

The VisText target schema and a representative chart-to-RDF example are jointly shown in Figure~\ref{fig:vistext_example}. The schema is intentionally small so that evaluation focuses on chart semantics and data values. Not every original VisText item yields a reliable RDF reference graph. Some original labels contain damaged categories, inconsistent tabular annotations, or insufficient information to recover the plotted data. Such items are excluded from labelled evaluation, while the remaining items are released as RDF/Turtle references.

\subsection{Prompting Strategies}\label{subsec:prompting}

All generation strategies use a dataset-specific zero-shot system prompt that defines the task, schema, and output constraints. The complete zero-shot system prompts are provided in~\ref{app:system_prompts}.

\subsubsection{Zero-Shot Prompting}
The model receives only the system prompt, a short user instruction, and the target image. This setting tests whether the model can infer the required graph directly from the task description and schema.

\subsubsection{Static One-Shot Prompting}
The model receives one curated image-to-RDF example before the target image. For VisText, the static one-shot example is a bar chart because bar charts are common in the dataset. For Diagram2Graph, the one-shot example is a representative diagram.

\subsubsection{Dynamic One-Shot Prompting}
Dynamic one-shot prompting is used for VisText because the dataset contains multiple chart types. A preliminary classification step assigns the input chart to the bar, line, or area category. The extraction prompt then uses the example and chart-specific instructions corresponding to that predicted type. Diagram2Graph does not use dynamic one-shot prompting because all inputs are diagrams.

\subsubsection{Few-Shot Prompting}
Few-shot prompting provides all curated examples for the dataset. VisText uses one bar chart, one line chart, and one area chart. Diagram2Graph uses three diagram examples.

\subsection{Generation Model and Validity Criterion}

All image-to-RDF experiments use Gemini 3 Flash. The model is not fine-tuned on either labelled dataset. A generated output is considered eligible for evaluation only if it can be parsed as RDF/Turtle.

\section{Evaluation on Labelled Datasets}\label{sec:evaluation}

\subsection{Traditional Graph Metrics for Labelled Datasets}

For VisText and Diagram2Graph, predicted RDF graphs are compared with reference RDF graphs after parsing and normalization. Following recent work on LLM-based KG construction evaluation \citep{ghanemcruz2025kgc}, we report a set of complementary metrics rather than a single score because different metrics measure different properties of graph quality.

The metric set is organized into four categories:

\begin{itemize}
    \item \textbf{Exact triple overlap.} Triple-match precision, recall, and F1 measure exact overlap between predicted and reference triples. This is the strictest content-oriented metric family and directly penalizes missing or hallucinated triples. Triple-match accuracy is also reported as a prediction-oriented exact-match rate, measuring the proportion of predicted triples that appear in the reference graph.
    \item \textbf{Graph edit distance.} Normalized graph edit distance (GED) treats each RDF graph as a labelled directed multigraph and estimates the normalized edit cost required to transform the predicted graph into the reference graph. This metric captures structural differences that may not be visible from aggregate triple counts alone.
    \item \textbf{Lexical triple similarity.} BLEU and ROUGE compare serialized triples as textual units under one-to-one assignment \citep{bleu,rouge}. These metrics provide softer lexical similarity signals when a predicted triple is close to a reference triple but not exactly identical.
    \item \textbf{Embedding-based triple similarity.} G-BERTScore applies contextual embedding similarity to serialized triples and is intended to capture semantically close but lexically non-identical triples \citep{bertscore}.
\end{itemize}

The formal definitions used in the paper are provided in~\ref{app:metric_definitions}.

\subsection{VisText Evaluation Modes and Numeric Tolerance}

The VisText schema is designed to be semantically complete: its full RDF graph can be used directly as a chart knowledge graph because it includes chart type, axis resources, datapoint resources, and membership relations. For evaluation, however, this completeness can overestimate model performance because many triples are fixed by the schema once the model has adopted the expected output pattern. We therefore report both full-graph and content-only modes. Full-graph mode evaluates every normalized triple. Content-only mode retains literal-valued triples and the chart-type triple, while omitting fixed schema-completion triples. In Figure~\ref{fig:vistext_example}, for example, triples such as \texttt{:XAxis a :Axis}, \texttt{:DataPoint1 a :DataPoint}, and \texttt{:DataPoint1 :belongsTo :Chart} are omitted in content-only mode, whereas triples such as \texttt{:Chart :title "..."}, \texttt{:XAxis :title "Year"}, \texttt{:DataPoint1 :xValue "Dec 31, 1953"}, \texttt{:DataPoint1 :yValue "1"}, and \texttt{:Chart a :AreaChart} are retained.

VisText evaluation also includes an optional relative numeric tolerance for quantity-like datapoint values. This is needed because the model receives only the chart image: for many line and area charts, a visually reasonable estimate may be close to the reference value but not exactly identical. The tolerance is applied only to exact structural metrics, namely triple-match precision, recall, F1, triple-match accuracy, and normalized GED. Lexical and embedding-based metrics, including BLEU, ROUGE, and G-BERTScore, are left unchanged so that tolerance-adjusted exact matching and soft textual similarity remain separate evaluation signals.

\subsection{LLM-as-a-Judge Validation Framework}

The LLM-as-a-judge framework is evaluated on the labelled datasets before being used on unlabelled data. It uses OpenAI GPT-5-mini \citep{openai2025gpt5systemcard} as the judge model, whereas image-to-RDF generation uses Gemini 3 Flash. Using a different model family for judging reduces the risk that the evaluator systematically favours generations from its own model family \citep{spiliopoulou2025playfavorites}. Judge outputs are constrained through structured response schemas, so the evaluation produces typed scores and preferences.

The judge is used in two complementary modes. In direct scoring, the judge receives the source image and one candidate RDF/Turtle graph. It assigns five criterion scores and one overall score on a 1-to-5 scale. In pairwise comparison, the judge receives the same source image and two candidate graphs generated by different prompting strategies. It selects the better graph for each criterion and gives an overall preference. Direct scoring supports absolute quality analysis, while pairwise comparison supports strategy ranking without requiring the judge to calibrate scores across unrelated images.

\section{Discussion}\label{sec:discussion}

% The main experimental results are interpreted with respect to the different error profiles of charts and diagrams. In VisText, much of the difficulty lies in recovering complete and numerically accurate datapoints from visual marks. Exact triple matching is therefore a strict measure of graph correctness, but it may underestimate cases where a predicted value is visually plausible and close to the reference value. The tolerance analysis addresses this issue conservatively by requiring exact matching on the opposite datapoint coordinate before numeric tolerance is applied. In Diagram2Graph, by contrast, the central difficulty is topological: a small number of incorrect or missing edges can alter the procedure represented by the diagram even when many node labels are correct.

% The use of multiple metrics is necessary because no single metric fully characterizes image-to-RDF quality. Triple-match metrics provide direct evidence about exact graph overlap. Normalized GED captures structural graph differences. BLEU, ROUGE, and G-BERTScore provide softer similarity signals for cases where a prediction is lexically or semantically close but not exactly identical to the reference graph. These metrics are read together, especially when comparing prompting strategies across visual genres.

% The LLM-as-a-judge framework is also interpreted cautiously. Its purpose is not to replace labelled evaluation when reference graphs are available. Rather, it provides a possible evaluation mechanism for unlabelled image collections after it has been validated against traditional metrics on labelled datasets. Agreement between judge preferences and graph-matching metrics would support its use on unlabelled data; disagreement would indicate that the judge rubric or prompting requires further calibration.
\subsection{VisText Numeric Tolerance Sensitivity}

The numeric-tolerance analysis in Table~\ref{tab:vistext_tolerance_results} indicates that many visually inferred datapoint values are very close to the reference values even when they are not exact string matches. Under zero-shot prompting, 27.6\% of eligible numeric datapoint literals match exactly. Introducing only a 0.5\% relative tolerance increases the matched-literal ratio to 53.2\%, nearly doubling the exact-match result. At 1\% tolerance, 67.6\% of eligible numeric literals are matched, and at 2\% tolerance the matched-literal ratio reaches 79.0\%.

This result is important because the model predicts these values directly from the chart image, without access to the underlying data table. The tolerance sweep therefore suggests that many numerical errors are small visual-estimation deviations rather than failures to recover the chart content. An extended sweep to 3\%, 4\%, and 5\% further raises the matched-literal ratio to 83.9\%, 86.8\%, and 88.7\%, respectively, but the largest gain already occurs within the first 2\% tolerance interval. We therefore interpret the 0--2\% range as the most informative region for characterizing typical VLM value-estimation accuracy in this task: most recoverable numeric datapoint predictions are close to the reference values, even under a strict image-only extraction setting.

\section{Zero-Shot System Prompts}\label{app:system_prompts}

\subsection{VisText Zero-Shot System Prompt}
\begin{lstlisting}[style=markdownstyle]
# Role
You are a multimodal knowledge graph construction system.
# Task
Read one chart image and output only valid RDF/Turtle encoding the chart's semantic content.
## Output
- RDF/Turtle only; no explanations, Markdown fences, comments, JSON, XML, YAML, or prose.
- Use exactly:
```turtle
@prefix : <http://example.org/vistext#> .
```
## Chart Types
- `:BarChart`, `:LineChart`, `:AreaChart`
## Schema
- Classes: `:BarChart`, `:LineChart`, `:AreaChart`, `:Axis`, `:DataPoint`
- Properties: `:title`, `:xAxis`, `:yAxis`, `:xValue`, `:yValue`, `:belongsTo`
## Required Structure
```turtle
:Chart a :BarChart / :LineChart / :AreaChart ;
    :title "..." ;
    :xAxis :XAxis ;
    :yAxis :YAxis .
:XAxis a :Axis ;
    :title "..." .
:YAxis a :Axis ;
    :title "..." .
:DataPoint1 a :DataPoint ;
    :xValue "..." ;
    :yValue "..." ;
    :belongsTo :Chart .
```
## Extraction Rules
- Extract the chart title exactly as shown.
- Extract visible x-axis and y-axis titles exactly as shown; omit missing axis-title triples rather than inventing them.
- For vertical bar charts, `xValue` is the category and `yValue` is the numeric bar value.
- For horizontal bar charts, `xValue` is the numeric bar value and `yValue` is the category.
- For line and area charts, `xValue` is the x-axis coordinate/category/time value and `yValue` is the numeric value.
- Infer the intended number of datapoints from chart semantics, especially title, axis labels, visible ticks, temporal range, and categorical range.
- For temporal annual line/area charts, normalize annual observations as `"Dec 31, YYYY"`.
- Represent all values as quoted strings without datatype annotations.
- Prefer exact values when readable; otherwise estimate values from axis ticks and geometry without inventing unsupported facts.
\end{lstlisting}

\subsection{Diagram2Graph Zero-Shot System Prompt}
\begin{lstlisting}[style=markdownstyle]
# Role
You are a diagram-to-graph extractor.
# Task
Given one flowchart or diagram image, output only valid RDF/Turtle using the lightweight diagram2graph vocabulary.
## Output
- RDF/Turtle only; no explanations, headings, comments, Markdown fences, JSON, XML, YAML, or extra text.
- Use exactly one prefix:
```turtle
@prefix : <http://example.org/diagram2graph#> .
```
## Ontology
- Node classes: `:Node`, `:Start`, `:Process`, `:Decision`, `:Delay`, `:Terminator`
- Shape values: `:StartEvent`, `:EndEvent`, `:Task`, `:Gateway`, `:DataStore`
- Edge classes: `:Edge`, `:Solid`, `:Dashed`
- Relationship values: `:Follows`, `:Branches`, `:DependsOn`
- Node properties: `:label`, `:shape`
- Edge properties: `:source`, `:target`, `:relationshipType`, `:relationshipValue`
## Resource Naming
- Name nodes as `:NodeN` and edges as `:EdgeN`.
- Number nodes and edges in visual reading order when explicit identifiers are absent.
## Node Triples
```turtle
:NodeN a :NodeType, :Node ;
    :label "exact visible text from the shape" ;
    :shape :ShapeValue .
```
## Edge Triples
```turtle
:EdgeN a :LineStyle, :Edge ;
    :source :NodeS ;
    :target :NodeT ;
    :relationshipType :RelationshipType .
```
If the arrow has a visible label, add:
```turtle
:relationshipValue "exact visible arrow label" .
```
## Constraints
- Do not emit direct node-to-node relationship triples.
- Do not use `rdfs:label`; use `:label`.
- Preserve visible text exactly.
- Every edge source and target must reference an emitted node resource.
- Every Turtle statement must end with a period.
\end{lstlisting}

\subsection{Soil-Health Zero-Shot System Prompt}
\begin{lstlisting}[style=markdownstyle]
# Role
You are a multimodal knowledge-extraction agent for soil-health figures and tables.
# Task
Read one soil-health image and output only valid RDF/Turtle triples that encode the concepts and relationships explicitly visible in the image.
## Output
- RDF/Turtle only; no explanations, headings, comments, Markdown fences, JSON, XML, or YAML.
- Emit these two prefixes first and use only these prefixes:
```turtle
@prefix she: <https://soilwise-he.github.io/soil-health#> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .
```
## Concept Nodes
- Create a `she:` PascalCase URI for each visible concept and declare it as `skos:Concept`.
- Add `skos:prefLabel` using the visible label text in lowercase when it is a normal phrase.
- Preserve meaningful symbols and abbreviations through `skos:altLabel`, `she:hasAbbreviation`, or `she:hasSymbol` when visible.
- Use `skos:definition` or `skos:note` for visible definitions, notes, legends, or footnotes when they add semantic meaning.
- Deduplicate repeated labels.
## Relationships
- Use `skos:narrower` or `skos:broader` for containment, grouping, table header hierarchy, bullets, tree levels, and parent-child boxes.
- Use `skos:related` for visible associations where no direction or stronger relation is clear.
- For explicit non-hierarchical semantics, create a clear `she:` camelCase property such as `she:affects`, `she:measures`, `she:hasIndicator`, `she:isBasedOn`, `she:hasPositiveImpactOn`, `she:hasNegativeImpactOn`, or `she:hasNeutralImpactOn`.
- Respect arrow direction and labelled connector direction when visible.
- Do not invent concepts or relations not visible or directly implied by layout, legend, or labels.
## Tables
- Extract row headers, column headers, grouped headers, legend labels, and semantically meaningful cell values.
- For impact matrices, map positive impact or `+` to `she:hasPositiveImpactOn`, negative impact or `-` to `she:hasNegativeImpactOn`, and neutral/unknown/indifferent/indiff. to `she:hasNeutralImpactOn`.
## Figures
- Extract boxes, headings, lists, diagram regions, arrows, captions, legends, and notes when they carry semantic content.
- Model group boxes and regions with `skos:narrower`.
- Model arrows or connectors with the clearest `she:` camelCase property.
## Final Checklist
- The output starts with exactly the `she:` and `skos:` prefixes.
- Every concept URI is in the `she:` namespace and has `skos:Concept` plus `skos:prefLabel`.
- Turtle syntax is valid.
\end{lstlisting}

\section{Mathematical Definitions of Evaluation Metrics}\label{app:metric_definitions}

This appendix formalizes the graph metrics used in our evaluation implementation. The metric family follows prior LLM-based KG construction evaluation work \citep{ghanemcruz2025kgc}, while the definitions below state the exact variants used in this paper.

Let $\mathcal{I}=\{1,\ldots,N\}$ be the evaluated image set. For image $i$, let $G_i$ be the set of reference triples and $P_i$ the set of predicted triples after RDF parsing, graph projection, and normalization. A triple is written as $t=(s,p,o)$, and normalization lowercases and strips whitespace from all three terms. When a denominator is zero, the corresponding score is defined as zero.

\subsection{Exact Triple-Match Precision, Recall, and F1}
Exact triple matching treats $G_i$ and $P_i$ as sets. The micro-averaged true positives, false positives, and false negatives are
\[
TP=\sum_{i\in\mathcal{I}} |G_i\cap P_i|,\quad
FP=\sum_{i\in\mathcal{I}} |P_i\setminus G_i|,\quad
FN=\sum_{i\in\mathcal{I}} |G_i\setminus P_i|.
\]
The reported exact triple-match precision, recall, and F1 are
\[
\mathrm{P}_{T}=\frac{TP}{TP+FP},\quad
\mathrm{R}_{T}=\frac{TP}{TP+FN},\quad
\mathrm{F1}_{T}=\frac{2\mathrm{P}_{T}\mathrm{R}_{T}}{\mathrm{P}_{T}+\mathrm{R}_{T}}.
\]

\subsection{Triple-Match Accuracy}
Triple-match accuracy is computed per image as the fraction of predicted triples that are present in the reference graph:
\[
\mathrm{Acc}_{T,i}=\frac{|P_i\cap G_i|}{|P_i|}.
\]
The reported value is the arithmetic mean
\[
\overline{\mathrm{Acc}}_{T}=\frac{1}{N}\sum_{i\in\mathcal{I}}\mathrm{Acc}_{T,i}.
\]
This metric is prediction-oriented: it rewards predicted triples that exactly match the reference graph and penalizes hallucinated predicted triples, but it does not directly penalize omitted reference triples except through the denominator of other metrics.

\subsection{Normalized Graph Edit Distance}
Each triple set $S$ is converted into a labelled directed multigraph $\Phi(S)=(V_S,E_S)$:
\[
V_S=\{s\mid (s,p,o)\in S\}\cup \{o\mid (s,p,o)\in S\},
\]
\[
E_S=\{(s,o,p)\mid (s,p,o)\in S\},
\]
where node labels are the normalized RDF terms and edge labels are predicates. Let
\[
d_i=\mathrm{GED}\bigl(\Phi(G_i),\Phi(P_i)\bigr)
\]
denote the graph edit distance under exact node-label and edge-label matching. In implementation, this value is estimated with NetworkX iterative graph-edit optimization. The normalized graph edit distance for image $i$ is
\[
\mathrm{nGED}_i=
\frac{d_i}
{|V_{G_i}|+|E_{G_i}|+|V_{P_i}|+|E_{P_i}|},
\]
and the reported score is
\[
\overline{\mathrm{nGED}}=\frac{1}{N}\sum_{i\in\mathcal{I}}\mathrm{nGED}_i.
\]
Lower values indicate smaller structural distance between predicted and reference graphs.

\subsection{Assignment-Based Textual Graph Similarity}
BLEU, ROUGE, and G-BERTScore are computed over serialized triples. Let $\sigma(t)$ denote the textual serialization of triple $t$. For a similarity function $m$, define the pairwise score matrix for image $i$ as
\[
M^{(m)}_{ab}=m\bigl(\sigma(p_{ia}),\sigma(g_{ib})\bigr),
\quad p_{ia}\in P_i,\ g_{ib}\in G_i .
\]
A one-to-one alignment between predicted and reference triples is selected by maximum-weight bipartite matching:
\[
A_i^{(m)}=\arg\max_{A}\sum_{(a,b)\in A}M^{(m)}_{ab}.
\]
The per-image precision, recall, and F1 for metric $m$ are then
\[
\mathrm{P}^{(m)}_i=
\frac{\sum_{(a,b)\in A_i^{(m)}}M^{(m)}_{ab}}{|P_i|},\quad
\mathrm{R}^{(m)}_i=
\frac{\sum_{(a,b)\in A_i^{(m)}}M^{(m)}_{ab}}{|G_i|},
\]
\[
\mathrm{F1}^{(m)}_i=
\frac{2\mathrm{P}^{(m)}_i\mathrm{R}^{(m)}_i}
{\mathrm{P}^{(m)}_i+\mathrm{R}^{(m)}_i}.
\]
The paper reports arithmetic means over images for $\mathrm{P}^{(m)}$, $\mathrm{R}^{(m)}$, and $\mathrm{F1}^{(m)}$.

\subsection{BLEU}
For BLEU, $m_{\mathrm{BLEU}}(\sigma(p),\sigma(g))$ is sentence-level BLEU with the predicted serialized triple as candidate and the reference serialized triple as the single reference \citep{bleu}. The implementation uses NLTK sentence BLEU with smoothing method 1.

\subsection{ROUGE}
For ROUGE, $m_{\mathrm{ROUGE}}(\sigma(p),\sigma(g))$ is ROUGE-2 precision between the predicted serialized triple and the reference serialized triple \citep{rouge}. This pairwise ROUGE-2 precision is used as the assignment similarity; the reported ROUGE precision, recall, and F1 are then obtained from the assignment equations above.

\subsection{G-BERTScore}
For G-BERTScore, $m_{\mathrm{GBS}}(\sigma(p),\sigma(g))$ is BERTScore F1 between the predicted and reference serialized triples \citep{bertscore}. The implementation computes pairwise BERTScore without inverse-document-frequency weighting and applies the same maximum-weight assignment procedure used for BLEU and ROUGE.

\section{LLM-as-a-Judge Prompts}\label{app:judge_prompts}

\subsection{Direct Judge Prompt}
\begin{lstlisting}[style=markdownstyle]
# Role
You are an evaluator assessing an RDF/Turtle knowledge graph generated from an image. Judge whether the graph reflects the visible source image and is well constructed as a knowledge graph.
# Task
Evaluate the candidate RDF/Turtle graph against the source image using five KGEval-style criteria adapted to image-to-KG extraction:
1. Relevance: Does the graph focus on information that is visible and important in the image?
2. Factuality: Are entities, labels, values, relationships, and chart or table claims grounded in the image without hallucination?
3. Informativeness: Does the graph capture the major useful content, such as chart titles, axes, data points, table rows, columns, diagram nodes, and relationships?
4. Coherence: Is the RDF/Turtle graph internally consistent, parseable in meaning, and structurally suitable for a knowledge graph?
5. Specificity: Are triples precise enough to recover the key image content rather than using vague or generic placeholders?
Also assign an `overall_score` from 1 to 5 as a holistic quality score.
## Rating Scale
- `1`: unusable, unrelated, hallucinated, or incoherent.
- `2`: limited correct content with major omissions, hallucinations, or graph problems.
- `3`: partially correct but incomplete, noisy, or loosely aligned.
- `4`: mostly faithful and useful with minor omissions or local errors.
- `5`: faithful, informative, coherent, specific, and well aligned with the image.
## Evaluation Steps
1. Inspect the source image and identify its key visible content.
2. Review the RDF/Turtle graph and compare its triples against the image.
3. For each criterion, assess the graph using the rating scale and criterion guidelines.
4. Identify major errors that materially affect graph quality.
5. Return only the structured JSON object required by the response schema.
\end{lstlisting}

\subsection{Pairwise Judge Prompt}
\begin{lstlisting}[style=markdownstyle]
# Role
You are an evaluator comparing two RDF/Turtle knowledge graphs generated from the same source image. Decide which candidate better represents the visible image content as a useful knowledge graph.
# Task
Compare Candidate A and Candidate B using five KGEval-style criteria adapted to image-to-KG extraction:
1. Relevance: Which graph better focuses on visible, task-relevant image information?
2. Factuality: Which graph has fewer hallucinated or incorrect entities, values, labels, and relationships?
3. Informativeness: Which graph captures more of the important image content?
4. Coherence: Which graph is more internally consistent and better structured as RDF/Turtle?
5. Specificity: Which graph is more precise and less generic?
For each criterion, choose A, B, or tie. Then choose an overall winner. Use tie only when the candidates are meaningfully equivalent or when their errors balance out.
## Evaluation Steps
1. Inspect the source image and identify the key visible facts.
2. Analyze Candidate A and Candidate B independently.
3. Compare direct overlaps, missing elements, incorrect claims, and RDF/Turtle modelling quality.
4. Select a preference for each criterion.
5. Select the overall winner and confidence.
6. Return only the structured JSON object required by the response schema.
\end{lstlisting}
